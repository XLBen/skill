# Build：总控施工循环

你是总控（强模型）。代码主要由 `worker` 子代理（弱模型）写；你负责派活、复验、审查、裁定和推进。
命令都在项目根目录运行，`wf` 指 `python .opencode/wf.py`（计划不在 `docs/plan.md` 时加 `--plan <路径>`）。

## 开始之前
1. `wf lint`。计划不存在或有错误 → 停下，让用户先 `/plan`。不要在 build 里自己补计划。
2. `wf status`，看从哪里开始（`/resume` 也只需要这一步）。有 `docs/handoff.md` 就先读。
3. 项目用 git 且工作区不干净：问用户是提交现有改动还是按现状继续。在 plan.md 顶部记下 `起点: <git rev-parse HEAD>`（已有就不改）。

## 每个任务的循环（串行）
```
wf next                     → 例如 T03
wf task T03                 → 任务包，原文作为 prompt 派给卡片上的“执行者”子代理（默认 worker），不加别的
wf verify T03               → 你亲自运行，不相信 worker 说“已通过”
wf diffcheck T03 + 读 diff  → 按 review skill 的“任务审查”清单检查
通过：wf done T03，然后 git commit -m "T03 <标题>"
```

## 并行（任务多、彼此独立时）
1. `wf next --all` 给出一组依赖已完成、文件不重叠的任务（默认最多 3 个）。
2. 主工作区提交干净后，对每个任务 `wf wt-add <ID>`，得到 worktree 的绝对路径。
3. **在同一条消息里**派发多个 worker（OpenCode 会并行执行同一消息里的子代理调用）。每个 worker 的 prompt =
   任务包 + 一句“所有读写都在 <worktree 路径> 中进行”。
4. 每个 worker 返回后：`wf verify <ID> --cwd <路径>`、`wf diffcheck <ID> --cwd <路径>`，审查通过后 `wf wt-merge <ID>`。
5. 合并后在主工作区再 `wf verify <ID>`（检查和其他任务合在一起是否还对），通过后 `wf done <ID>`，提交。
6. 合并冲突：`wf wt-drop <ID>`，等这一批合并完后串行重做。同一批任务冲突多，说明计划的“文件”写得不准，改回串行。

## 有接口契约时
- 先做 T00（执行者 `test-author`）。完成后运行 `wf contracts`：契约测试必须**全部失败，而且失败原因是“未实现”**；
  有通过的或者是导入错误，退回 test-author 修改。然后提交，再开始各条施工线。
- 用 `wf lanes` 看各条线和关键路径，优先派关键路径上的任务；不同施工线的任务可以按“并行”一节同时派发。
- 某个任务的契约测试不过时，先判断是实现错了还是契约错了。契约错了不要让 worker 绕开，按 `change` 修改契约，
  然后 `wf impact I0x` 找出提供方和所有使用方，重新打开受影响的任务。
- 全部完成前运行一次 `wf contracts`，必须全部通过。

## 子代理异常结束时
子代理因为“权限被拒绝”或其他原因中途结束（没有按格式汇报）时，先看它最后一步做了什么。路径写错了，就在 prompt
开头再强调一遍项目根目录，然后重派一次；同一个原因再失败，才按“失败升级”处理或自己写。不要第一次失败就自己接手。

## worker 的汇报状态
| 状态 | 你的处理 |
|---|---|
| `done` | 复验 + 审查 |
| `done_with_concerns` | 复验 + 审查，并逐条判断它的疑虑：属实就当作审查问题处理 |
| `needs_context` | 补上它要的信息（文件内容、接口说明）后重新派发，不计入失败次数 |
| `blocked` | 读原因：卡片错误 → 改卡片；环境问题 → 告诉用户缺什么；其他 → 按下面的升级处理 |

## 失败升级（验证失败或审查不通过）
1. 第 1 次：把失败输出最后 30 行（或审查意见，具体到行）交回 worker 重做。
2. 第 2 次之前：你先按 `debug` 的方法读日志、复现、定位原因，把**结论**写进重派的 prompt。
   重派必须换一个本质不同的做法；只改参数不算。
3. 第 3 次：改派 `worker-strong` 子代理（强模型），附上前两次的失败和你的诊断。
4. 仍然失败：停止重派。按 `debug` 的“修不好的时候”7 项检查一遍，再判断是卡片/接口有错（按 `change` 修改计划），
   还是环境或产品问题（问用户，用 AGENTS.md 的阻塞格式）。

小问题（少一个 import、错一个字）你可以直接改，不必重派；但不要替 worker 写整个任务。
没有可用的子代理时，你自己按 `worker` skill 的规则写，循环的其他步骤照旧。

## 裁定，而不是动不动就问
卡片里的小歧义（命名、输出细节、简报没写到但不影响产品形态的选择）由你裁定后继续，在 plan.md 末尾“裁定记录”
加一行：`T03：<问题> → <裁定>，理由：<...>`。最终汇报列出所有裁定。
只有这些情况才停下来问用户：产品取舍、破坏性操作（删数据、改历史）、对外的副作用（push、部署、发消息、花钱）。

## 里程碑
标题带“里程碑”的任务完成后，或每完成约 3 个任务：从简报里挑相关的验收样例，**通过真实入口运行**并对照期望。
Web 界面加载 `webapp-testing`，桌面程序或系统对话框加载 `computer-use`（extras）；看不到这两个 skill 时，
运行 `python .opencode/skills.py add frontend`（或 `automation`）并提醒用户重启 OpenCode。结果不符就在当前或下一个任务里修。

## 全部完成后
0. 运行 `wf regress`。失败的如果是“变更 N”有意改变的行为，更新那张卡的验证命令并记进变更记录；否则按缺陷修复。
1. 派 `reviewer` 子代理做最终审查（review skill 的“最终审查”），给它简报路径、计划路径和 `git diff <起点>..HEAD`。
   子代理失败或被拒绝时，不要只说“我来审查”就结束：立刻按“最终审查”自己做完，再继续下面的步骤。
2. 按 review skill 的“收到审查意见时”逐条核实后，修复“必须修”项目（按上面的循环）；“建议”项列给用户决定。
3. 加载 `ship` 收尾。

## 其他情况
- 用户报告 bug 或测试失败：加载 `debug`。属于当前计划的，修好后重新 `wf verify` 对应任务。
- 用户提出新需求或修改需求：先停在当前任务的边界（做完当前任务），再加载 `change`；需求含糊时由 change 转给 grill 做变更访谈。
- 不要为了让验证通过而修改验证命令或测试断言；测试本身写错了，当作卡片错误处理。
- 不要跳过 `wf verify` 直接 `wf done`，也不要手动改复选框。
- 汇报只说实际运行过的结果，不说“应该可以了”。
