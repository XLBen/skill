# Change：为变更写计划

和 grill → plan 对应：**grill 的变更访谈**把需求问成简报里的“变更 N”，**change** 把它设计成任务卡，再交给 `build`。
原则：只动受影响的部分。不重写计划，不重做没受影响的任务，已完成任务的代码默认是正确的。
`wf` 指 `python .opencode/wf.py`。

## 0. 先确认需求清楚
- 简报里已经有本次的“变更 N”（grill 写的）→ 以它为准，进入第 1 步。
- 没有，且用户的话含糊、或者涉及两个以上产品取舍 → 加载 `grill` 做变更访谈，确认后再回来。
- 没有，但需求清楚、最多一个取舍 → 那个取舍用 grill 的单题格式问（附推荐答案），
  然后按 grill 的“变更 N”格式写进简报，给用户看一眼。
- 是缺陷（简报和计划本来就要求这样，是代码没做对）→ 加载 `debug`，不走变更流程。

## 1. 分类
| 类型 | 判断方法 |
|---|---|
| 新增 | 不需要改已有的共享接口和已有行为 |
| 修改 | 已有的输出、签名、数据格式要变 |
| 设计修正 | 施工中发现库/API/环境做不到计划里的写法 |

分不清“新增”还是“修改”时，按“修改”处理。

## 2. 设计（plan 第 1、2 步的规则，只针对这次变更）
- 变更引入新的通用组件时，按 plan 第 1 步“先找现成的”处理。需要新的框架或库时，按 plan 的要求核实 API 出处；有会让变更作废的未知点，先安排 probe 任务。
- **共享接口**：新增的定义直接加；修改的定义直接改，并在 plan.md 末尾“变更记录”加一行：
  `变更 N：<改了什么>，原因：<...>`。
- **错误策略**：只加“变更 N”要求的失败处理。
- 运行 `wf impact <被改的接口名或文件>`，列出受影响的任务。有接口契约时，改契约要同时改它的示例和契约测试，
  `wf impact I0x` 会列出提供方和所有使用方；新增跨施工线的接口时也补一条契约。

## 3. 写任务卡（plan 第 3、4 步的规则）
- 新任务追加到 plan.md 末尾，编号接着往后排（已有 T01–T06，就从 T07 开始）。纵向切片、最多 4 个文件、验证命令断言内容。
- 受影响的**已完成**任务：
  - 只需改代码、验证命令不变 → 追加一个修改任务，依赖写原任务；
  - 验证命令本身也要改（行为有意改变）→ 改那张卡的验证命令，再 `wf reopen <ID>`。
- 受影响的未完成任务：直接改卡片。
- “变更 N”里的“保持不变”项，确认有已完成任务的验证命令覆盖它；没有就在新任务里加一条验证。

## 4. 自检后发布
运行 `wf lint`，修到没有错误。然后回答，有问题就改：
1. “变更 N”的每条验收样例（新增 / 修改 / 保持）由哪个任务、哪条验证覆盖？
2. 被修改的共享接口，`wf impact` 列出的每个任务都处理了吗？
3. 随便挑一张新卡，只看共享接口和这张卡，弱模型能直接动手吗？
4. 有没有顺手加进来、但“变更 N”没要求的功能或错误处理？有就删掉。

新增超过 3 个任务、或者修改了共享接口时，派 `reviewer` 做计划审查（review skill 的“计划审查”，只审这次变更的部分）。

## 5. 交付
告诉用户：变更类型、新增 / 重新打开 / 修改的任务、改了哪些共享接口、风险。
下一步：`/build`。没有命令时（用户直接提的需求）由同一个会话接着加载 `build` 施工。
build 全部完成时会运行 `wf regress`：失败的如果是这次有意改变的行为，更新那张卡的验证命令并记进变更记录；否则按缺陷处理。

## 汇报
`变更 N：<类型> | 新增任务: ... | 重新打开: ... | 修改了接口: ... | 下一步: /build`
