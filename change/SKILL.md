# Change：在已有计划上做变更

原则：**只动受影响的部分。**不重写计划，不重做没受影响的任务，已完成任务的代码默认是正确的。
`wf` 指 `python .opencode/wf.py`。

## 1. 分类
先读用户的话、`docs/brief.md`、`docs/plan.md` 的共享接口和任务标题，然后判断属于哪一类：

| 类型 | 判断方法 | 去向 |
|---|---|---|
| 新增功能 | 不需要改已有的共享接口和已有行为 | 第 2 步 |
| 修改行为或接口 | 已有的输出、签名、数据格式要变 | 第 3 步 |
| 缺陷 | 计划和简报本来就要求这样，是代码没做对 | 加载 `debug`，不走变更流程 |
| 设计假设不成立 | 施工中发现库/API/环境做不到计划里的写法 | 第 3 步，原因写“设计修正” |

分不清是“新增”还是“修改”时，按“修改”处理。
需要用户做产品取舍时，用 grill 的单题格式问**一个**问题（附推荐答案），不要重新做一次完整的 grill。

## 2. 新增功能
1. 在简报末尾追加：
   ```
   ## 变更 N（日期）
   用户原话: ...
   新增验收样例:
   | 输入 | 期望结果 |
   ```
2. 共享接口里只**新增**定义，不修改已有定义。新需求要求处理的失败，加进“错误策略”（只加简报里写到的）。
3. 在 plan.md 末尾追加任务，编号接着往后排（已有 T01–T06，就从 T07 开始）。卡片规则和 plan skill 相同：
   纵向切片、最多 4 个文件、验证命令断言内容。
4. 运行 `wf lint`。

## 3. 修改行为或接口
1. 简报追加“变更 N”，写清楚旧行为 → 新行为。
2. 在共享接口里直接改定义，并在 plan.md 末尾的“变更记录”加一行：`变更 N：<改了什么>，原因：<...>`。
3. 运行 `wf impact <被改的接口名或文件>`，找出提到它的任务。
4. 对每个**已完成**的受影响任务：
   - 只需要改代码、验证命令不变 → 追加一个修改任务，依赖写原任务；
   - 原任务的验证命令本身也要改 → 修改那张卡的验证命令，再 `wf reopen <ID>`，让它重新施工。
5. 未完成的受影响任务：直接修改卡片。
6. 运行 `wf lint`。

## 4. 施工和回归
- 按 `build` 的循环施工新增或重新打开的任务。
- 全部完成后运行 `wf regress`：重跑所有已完成任务的验证命令。
  - 失败的任务如果是这次变更**有意改变**的行为，就更新那张卡的验证命令并在变更记录里说明；
  - 否则就是回归缺陷，加载 `debug` 修复。
- 用简报里新增的验收样例做一次端到端检查。

## 汇报
`变更 N：<类型> | 新增任务: ... | 重新打开: ... | 修改了接口: ... | 回归: <通过数>/<总数>`
