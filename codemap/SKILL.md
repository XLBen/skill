# Codemap：一页仓库地图

目的：让规划者不用每次重读整个仓库，让 worker 遵循现有写法、复用已有模块，而不是重新造轮子。

## 步骤
1. 读 README、依赖清单（package.json / pyproject.toml / go.mod 等）、顶层目录、入口文件、几个代表性模块和测试。
2. **实际运行**安装、测试、启动命令中便宜且安全的那些（不连生产环境、不改数据）。记录真实可用的命令；
   失败的命令记录失败原因。
3. 写 `docs/codemap.md`，不超过 80 行，格式如下。只写读过代码或运行过命令确认的内容；不确定的标“未确认”。
4. 已有 codemap 时，只更新和本次工作相关、已经变化的部分。

## 格式

```markdown
# Codemap
更新: <日期>，基于提交 <git rev-parse --short HEAD>

## 项目
一句话：它是做什么的，谁在用。

## 命令（本机实测）
| 用途 | 命令 | 结果 |
|---|---|---|
| 安装 | ... | 通过 |
| 测试 | ... | 通过，N 个测试 |
| 运行 | ... | ... |

## 目录
| 路径 | 职责 |
|---|---|

## 入口与主流程
入口文件 → 主要调用链（一两行）。

## 惯用写法
- 错误处理：项目里实际怎么做（抛异常 / 返回错误码 / Result 类型）
- 测试：框架、文件位置、命名
- 风格：格式化工具、命名约定

## 可复用模块
| 模块 | 提供什么 |
|---|---|
（新代码应优先使用这些，而不是重写）

## 注意
- 容易踩的坑、生成的文件、不要手动修改的目录
```

不要写成架构评审，也不要提出改进建议；那是另外的工作。
