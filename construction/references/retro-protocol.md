# 竣工复盘协议（retro-protocol）

竣工不是终点——答辩和施工过程里踩过的坑，不沉淀就会在下一个项目重踩一次。复盘把"这次为什么卡"变成"下次第一章就写对"。

## 何时做

- 竣工报告输出之后、交接块之前，追加一次复盘（读 build-log 全部"待议"与重试记录）。
- CR 关闭（closed）超过 2 单的工程，无论是否竣工，都值得复盘一次。
- 用户说"不复盘"→ 跳过，交接块照常输出。

## 输入（只读这三个来源，不靠回忆）

| 来源 | 找什么 |
|---|---|
| `docs/defense-log.md` | 哪几类问题反复出现（≥2 轮同攻击面）；哪些硬伤暴露得太晚 |
| `docs/build-log.md` | 重试 ≥2 次的步骤；全部"待议"条目及其去向 |
| `docs/PLAN.md`《变更单》 | 每个 CR 的证伪对象：论文哪一章的判断错了 |

## 产出（三张清单，全部落盘）

```markdown
## 复盘 — <项目名>（日期）
### 1. 章程增补建议（→ docs/defense-charter.md）
- 建议新增 C-xx：<这次晚发现的硬伤，写成可判定条目>
### 2. 论文模板偏差（→ 本次记录，供下次立项注意）
- <如：§6 验证写成了存在性检查而非行为检查，导致 S-04 返工>
### 3. 施工程序问题（→ 如属本 skill 缺陷，向 skill 维护者反馈）
- <如：验收命令依赖了未来步骤的产物，规划时应拆步>
```

## 规则

1. 每条建议必须能追溯到具体事件（轮次/步骤/CR 编号），不许空谈。
2. 章程增补是**建议**：展示给用户，用户确认后才写入 `docs/defense-charter.md`；未确认的留在复盘记录里。
3. 复盘不改任何已验收的东西——发现遗留缺陷走正常变更单流程，不借复盘之名返工。
4. 交接块在复盘之后输出，追加一行：`- 复盘：见 build-log《复盘》节（<n> 条章程增补建议）`。
