# Debug：先复现，再修复

## 1. 复现
- 找到能稳定触发问题的最小命令或输入，记录确切的错误文本和退出码。
- 复现不了：先缩小条件（数据、顺序、环境），不要凭猜测修改。

## 2. 定位
- 读真实的代码和日志，从出错的位置沿调用链往回找，找到错误值第一次出现的地方。
- 找一条正常的路径（另一个输入、旧版本），对比它和失败路径的差别。
- 用一句话写出结论：“问题出在 X，因为 Y 已经排除（依据：…）”。

## 3. 确认根因
- 修改之前，先用一个最小实验证明根因（加一行打印、换一个输入、单独运行那个函数）。
- 一次只改一个变量。改了好几处才“好了”，就说明还没找到根因。
- 说“环境问题/权限问题/依赖版本问题”之前，要先有实验证据。

## 4. 修复并验证
- 在根因所在的层做最小修复。不要在下游加 try/except 或空值检查来掩盖问题。
- 修改一个函数之前，搜索它的所有调用方。在所有调用方都会经过的地方修一次，比在报告提到的那一处打补丁更小，也不会漏掉其他调用方。
- 原来的复现命令现在通过；再运行受影响部分的测试。
- 能稳定复现的缺陷，补一个回归测试。
- 检查同样的错误写法在别处有没有出现。

## 修不好的时候
- 第 2 次失败后，换一个**本质不同**的方法。只改参数、换个写法再试不算换方法。
- 再次运行并失败才算一次失败；读文件、搜索没结果、等待用户不算。
- 第 3 次失败前，逐项确认下面 7 件事，每项写“已做 / 不适用（理由）/ 做不了（证据）”：
  1. 完整读过错误输出和上下文了吗？
  2. 搜索过错误原文、官方文档、仓库里的类似用法吗？
  3. 读过出错位置的源码和配置吗？
  4. 用工具确认过版本、路径、权限、依赖、输入，而不是凭假设？
  5. 试过推翻最初的假设吗？
  6. 在最小范围内复现了吗？
  7. 换过工具、方法或技术路线吗？
- 仍然不行：停下，把这 7 项结果、已排除的原因和两个可选方案告诉用户，不要第 4 次重试。

## 汇报
`根因: <已证实的一句话，或“未确认”> | 依据: <实验或日志> | 修复: <改了什么> | 验证: <命令和结果>`
