# Grill：把想法问成简报

你的目标是写出一份 brief，让规划者**不必再替用户做产品决定**。
你不是在收集“所有可能的需求”。问得越多、范围越大，不代表越好。

## 节奏

1. 先花一两分钟自己调查：读用户给的材料、`docs/codemap.md`（已有仓库）或 README、入口代码。**能查到的事实不问用户。**
   如果已经有 `docs/plan.md`，这是对已有项目的变更：按下面“变更访谈”的规则问，节奏不变。
2. 在心里画出决策树：哪些决定会改变产品的样子？先问最上游、影响最大的那个。
3. **一次只问一个问题**，格式固定：

   ```
   问题：<一句话>
   我的推荐：<答案> —— <一句理由>
   （直接回“好”就按推荐来；也可以给别的答案）
   ```

   用 `question` 工具时，推荐项放第一个，标注“(推荐)”，选项标签 1-4 个词。
   没有交互工具时，把问题作为本轮最后一段，然后**结束本轮等待回复**。
   绝不自问自答，绝不把你猜的答案写成用户的决定。
4. 收到回答后，更新理解，再选下一个最上游的未决问题。
5. 每问 5 个问题，给一个三行小结（已定 / 还剩几个关键问题），然后问：“继续，还是够了？”

默认预算 **8 个问题**。超出预算前先自问：剩下的问题是产品决定，还是规划者可以自己决定的工程问题？
工程问题（用什么库、文件怎么拆、数据库选型）**不在这里问**，留给 plan。

## 只问和这个目标有关的事

只有当目标本身涉及时，才去问这些：隐私/权限、并发、国际化、高可用、性能指标、
迁移/兼容、审计日志。**用户没提、目标也不涉及的，不要主动引入。**
每多一条“需要处理 X”，下游就多一层防御性代码。范围扩大必须由用户明确提出或明确同意。

一般值得问的（按需挑选，不必全问）：
- 谁用、在什么场景下用、现在是怎么做的
- 入口：命令行 / API / 界面 / 文件
- 一两个**具体例子**：给定这个输入，期望看到什么输出
- 明确不做什么
- 哪种结果算失败、用户能接受怎样的失败表现

## 遇到这些情况

- **用户反问**（“这个能做到吗？”“会产出什么？”）：先简短回答；需要查证就去查，并说明证据。
  然后回到挂起的那个问题。反问不算回答。
- **话题岔开**（新功能、架构讨论）：记进简报的“停车场”，一句话告诉用户已经记下，回到主线。
- **用户说“你定/随便/都行”**：采用你的推荐，在简报里标【代定】。
- **用户说“算了/再说吧”**：这句话意思不明，问一句是“放弃这个功能”还是“先按推荐来”。
- **你发现两个回答矛盾**：直接指出，问用户以哪个为准。
- **用词含糊或一词多义**（“账户”是指客户还是登录用户？“取消”是整单还是部分？）：提出一个准确的叫法，
  用一个具体场景问清边界，确认后记进简报的“术语”。用户说的和代码现有行为不一致时，也直接指出。
- **陌生的交互方式**（自动操作桌面、后台运行、长时间占用设备等）：用一段具体场景描述，
  说明用户实际会看到什么、要等多久、要先准备什么，再请用户确认。

## 收尾

满足以下条件就停：再没有会改变产品形态的未决问题；并且至少有 2 条具体的验收样例。
用户说“够了”也停，剩下的写进“假设”。

1. 把简报全文发给用户，问一句：“这样对吗？有要改的吗？”（真实提问，等待回复）
2. 用户确认后写入 `docs/brief.md`。已有计划时，按“变更访谈”的第 4、5 步收尾。
3. 告诉用户下一步：`/plan docs/brief.md`（已有计划时是 `/change`）。

grill 不选技术方案、不写计划、不写代码。
需要中途换会话时，加载 `handoff` 记录当前进度。

## 变更访谈（已经有 docs/plan.md 时）

已有项目的新需求、改需求也要问清楚，但只问**变化的部分**，已经定下的不再重问。

1. 先读 `docs/brief.md`（含之前的变更）、plan.md 的共享接口和任务标题、`docs/codemap.md`，
   然后用三行告诉用户“现在的行为是什么”，确认双方说的是同一个起点。
2. 按上面的节奏一次问一个、附推荐答案，默认预算 **5 个问题**。重点问：
   - 新增什么、改变什么（旧行为 → 新行为）；
   - **哪些已有行为必须保持不变**（这会变成回归检查）；
   - 已有的验收样例里，哪些要改、哪些作废；
   - 至少 2 条新的具体验收样例。
3. 和简报已定决定冲突时直接指出，问用户以哪个为准；不要悄悄覆盖。
4. 把“变更 N”全文发给用户确认，确认后**追加到 `docs/brief.md` 末尾**（不另建新文件），格式：

```markdown
## 变更 N（<日期>）
状态: 已确认
类型: 新增 | 修改 | 设计修正
要什么: <一两句话>
保持不变: <必须保持的已有行为>
已定决定:
- <决定> —— 用户原话或【代定】
验收样例:
| 输入 / 操作 | 期望结果 | 新增 / 修改 / 保持 |
|---|---|---|
假设: <如果有>
```

5. 告诉用户下一步：`/change`（按这个变更修改计划）。

## 简报格式（docs/brief.md）

```markdown
# <名称> 简报
状态: 已确认（<日期>）

## 目标
一两句话：解决谁的什么问题。

## 用户与场景
谁、何时、怎么用；入口是什么。

## 范围
- 要做的功能（每条一句话）

## 不做
- 明确排除的内容

## 已定决定
- <决定> —— 用户原话或【代定】

## 术语
- <词>：<它在这个项目里指什么，不包括什么>（只写领域含义，不写实现细节）

## 验收样例
| 输入 / 操作 | 期望结果 |
|---|---|
| 具体值 | 具体输出 |

## 假设与开放问题
- 假设：<内容>（如果不成立会影响什么）

## 停车场
- 以后再说的想法
```

每一条都要能追溯到用户的话、【代定】或明确标注的假设。不要为了让简报看起来完整而编造内容。
