# Plan：给弱模型写施工图

读者是**没有聊天记录、能力较弱的执行模型**，每次只拿到一张任务卡和共享接口。
衡量计划好坏只看一个问题：**执行者拿到 T_k 之后，还需要自己做跨文件的决定吗？**
需要的话，那个决定就应该在计划里做掉。

格式见 `references/plan-template.md`，完整示例见 `references/example-plan.md`。

## 步骤

### 0. 估计规模
预计超过约 12 个任务时，不要一次写完所有任务卡：先写 `docs/roadmap.md`，列出 3-6 个阶段，每个阶段一句成果、
对应的简报验收样例、和前一阶段的依赖。然后**只为第一阶段**写详细的 plan.md。一个阶段完成并通过里程碑检查后，
把 plan.md 移到 `docs/plans/phase-N.md`，再根据实际代码写下一阶段的计划。后面阶段的细节等到时候再定，提前写只会过期。

### 1. 读输入，查事实
- 输入是 `docs/brief.md` 或一句明确的目标。简报里的范围、不做、验收样例都是硬约束：不扩大，也不缩小。
- 已有代码的仓库：先读 `docs/codemap.md`；没有或过期就先加载 `codemap` 生成。
- 按项目类型确认启用了合适的 extras 档案（`python .opencode/skills.py list`）。缺了就运行
  `python .opencode/skills.py use <档案...>`，并提醒用户重启 OpenCode。新项目：确认本机实际可用的工具命令（`npm` 还是 `pnpm` 等）。
- **先找现成的，再决定自己写**：设计里每个不是业务本身的组件（解析、调度、队列、缓存、重试、认证、命令行参数、
  数据校验、配置、日志……），依次查：项目已装的依赖 → 语言标准库 → 成熟的开源库。
  - 有候选时比较两三个：是否还在维护、许可、和项目技术栈是否匹配、引入成本。选定的写进“约定”，并写一句为什么不自己写。
  - 需要新增依赖时问用户一次；决定自己写的，在计划里写明理由（例如“只需 20 行，引入库不划算”）。
  - 不要把一个通用组件写成任务卡交给 worker 去实现——worker 只会照卡片做。
- 只查会让路线作废的事实：库能不能做到、API 实际叫什么、平台有什么限制。
- **框架和库的关键调用要有出处**：引用官方文档（写上链接和版本），或者在本机实测过（安装后读签名、跑一行代码）。
  不要凭记忆写 API；弱模型会照着计划写，计划里的错误 API 会直接变成错误代码。查不到的写进“风险与探针”。
  用到不熟悉的框架时，加载 `source-driven-development`（extras）按它的方法查文档；有 `context7_` 开头的工具时，用它按库名和版本取官方文档。
- 新项目选技术栈时按 `references/stack-choice.md`：从“在哪运行、谁来用、谁来维护、要不要花钱、数据放哪、要不要离线”推技术，
  默认选默认表里最简单的那一档，偏离要写理由；不要因为流行就选。
- 只有互斥的产品取舍才问用户；工程选型自己定，并写一句理由。
  同时满足三条的决定才单独记进计划的“## 决定”：以后改起来代价大、不看理由会让人意外、确实在几个方案里权衡过。其他决定不用记。

### 2. 设计（写进计划的前几节）
- **背景**：两三句话，worker 只靠这段理解全局。
- **架构**：文件表（文件 → 职责 → 对外接口）。已有仓库沿用现有结构。
- **约定**：语言版本、依赖、运行与测试命令、代码风格。
- **共享接口**：所有跨任务使用的类型、函数签名、数据格式、CLI 输出格式，**只在这里定义一次**，写成代码。
  开头列出简报“术语”里的词和对应的代码名称（类名、字段名），worker 拿到的任务包里有这一节，命名就能一致。
- **错误策略**：整份计划只有这一节讲错误处理。只列出简报验收样例和真实外部边界要求处理的失败，写明在哪一层处理、表现是什么。末尾固定写上：“其他异常直接抛出，不捕获、不兜底、不重试。”
  不要因为“可能会出错”就加条目；没有出现在简报里、也没有真实边界的失败，不处理。
  但这几类**必须**考虑并写进来：信任边界上的输入（用户输入、外部文件、网络响应）、可能丢数据的写操作、安全相关的检查。

### 3. 拆任务
- **T01 是端到端骨架**：用最少的代码打通“入口 → 核心 → 输出”，后续任务在这个可运行的骨架上扩展。
  项目还没有检查命令时，T01 同时按 `guardrails` 建立它，并写进计划的 `## 检查` 节。
- 每个任务是一个**纵向切片**：完成后能用一条命令验证一个用户可见的行为。不要拆成“写模型 / 写服务 / 写接口”这种横向分层。
- 每个任务**最多改 4 个文件（含测试）**，预计 diff 不超过约 150 行。超过就拆分。
- 每个任务只依赖前面的任务，不需要知道后面的任务。只写真实的依赖：没有依赖关系的任务可以并行施工，
  它们的“文件”也尽量不要重叠。
- 有会让路线作废的未知点时，先安排一个 **probe 任务**：写一段一次性代码回答一个具体问题（例如“这个 API 能不能分页”），
  验证命令打印答案；结论写回“风险与探针”节，probe 代码在下一个任务中删除。结论不成立就回来改计划。
- 标题加“（里程碑）”的任务完成后，会跑一次简报验收样例；一般每 3 个任务左右设一个。

**代码组织**（写进“约定”，由 worker 遵守）：
- 按职责分文件；单文件超过约 300 行就拆分；入口文件只做参数解析和调用。
- 不建 `utils.py` / `helpers.py` / `common.py` 这类杂物文件。
- 只有一种实现时，不建抽象基类、工厂或插件机制：只有一种实现的接口是假接口，有两种才是真的。

**模块要“深”**（设计架构表时逐个检查）：
- 删除测试：设想删掉这个模块。如果复杂度跟着消失，它只是转发一下的空壳，合并掉；如果复杂度会散到各个调用方，它才有存在的价值。
- 接口要小、实现可以多：调用方需要知道的东西（参数、调用顺序、错误、配置）越少越好。接口和实现差不多复杂时，说明切错了地方。
- 依赖从外面传进来，不在函数里自己创建；能返回结果就不要直接修改外部状态。这样测试可以直接走公开接口。
- 反过来也不要为了少改几行就把逻辑硬塞进一个文件或在下游打补丁：如果这样做会造成重复逻辑、
  让职责归属不清或掩盖根因，就安排一个重构任务，把逻辑放到负责它的那一层。

### 3.5 多条施工线时：契约优先
设计里有**两个以上组件**（前端和后端、解析和存储、采集和分析……）通过接口协作时就用，不看任务数量。
只有单一组件的小改动（全部逻辑在一两个文件里）才跳过。
目标：你定好接口和验收标准，各个子智能体只负责让自己那部分达标，彼此不需要知道对方怎么实现。
这样也节约注意力：每个 worker 的任务包里只有它提供和使用的那几条契约，看不到其他组件的细节；总控审查时也只需要对照契约。

1. **接口契约**：在计划里加 `## 接口契约` 节，每个跨施工线的接口一条：
   ```
   ### I01 parse_events(text) -> list[Event]
   提供: T03
   使用: T05, T07
   示例: 合法两行 → 2 个 Event；第 2 行缺字段 → InvalidBatch("invalid_event", 2)
   契约测试: python -m unittest tests.contracts.test_i01_parse_events
   ```
   示例尽量直接取自简报的验收样例。每条契约只有一个提供方；只在一个任务内部使用的函数不写契约。
2. **T00 接口骨架**（执行者 `test-author`，阻塞所有施工线）：建立全部接口的签名（函数体只抛“未实现”）和全部契约测试。
   T00 的验证只检查骨架能被导入；完成后由 build 运行 `wf contracts`，确认契约测试**全部因“未实现”而失败**。
3. **分配执行者**：每张卡写 `执行者:`——`backend-worker`、`frontend-worker`、`worker`（通用），难度高的直接写 `worker-strong`。
4. **能并行就不加依赖**：使用某个接口的任务只依赖 T00（骨架里已经有签名和契约），不依赖提供方任务；
   不同施工线的任务“文件”不要重叠。用 `wf lanes` 看各条线和关键路径，关键路径越短越好。
5. **集成里程碑**：各条线都完成后，安排一个标“里程碑”的集成任务，用简报的验收样例跑通整条链路。

`wf verify` 会自动运行任务所提供接口的契约测试；`wf task` 只把与这张卡相关的契约放进任务包。
契约在 T00 之后就算冻结，要改必须走 `change`。

**重构任务**（只改结构、不改行为）单独成卡，不和功能改动混在一张卡里：
- 先有能锁住现有行为的测试（没有就在前一张卡里补上），改前改后跑同一组验证命令，结果必须一致。
- 一张卡只移动一个职责边界（抽出一个模块、合并两处重复）；每张卡完成后程序都能运行、测试都通过。
- 公开接口、错误行为、输出顺序默认不变；要变就不是重构，按功能改动处理。
- 重构不新增依赖和配置。

### 4. 写任务卡
每张卡包含：状态复选框、依赖、文件、阅读（可选，要先读的现有文件）、接口（使用/提供）、要点（3-6 条，给出算法和关键调用，
难点可以给代码片段）、验证（```bash 代码块，每行一条命令）、完成标准。

- **验证命令必须断言内容**：单元测试，或 `python -c "assert ..."`。只看退出码或文件存在不算验证。
- **验证命令要能在 Windows、macOS、Linux 上运行**：Python 命令一律以 `python` 开头（wf 会换成当前解释器）；
  不用 grep/sed/cat 等工具，`python -c` 里用双引号包裹代码。非 Python 项目用项目自己的测试命令（`npm test` 等）。
- 测试只覆盖卡片描述的行为和错误策略里的条目，不为“可能的边界”编测试。
  简报里有特定风险（解析不可信输入、幂等、并发、故障恢复、数据迁移）时，加载 `testing` 选测试方法，并把选定的方法写进那张卡的“要点”。
- 卡片不写 TBD、TODO、待定、“适当处理”、“依此类推”、“参考上一任务”。

### 5. 自检后发布
运行 `python .opencode/wf.py lint`，修到没有错误。然后回答这 5 个问题，有问题就改计划：
1. 简报里的每条验收样例，分别由哪个任务实现、哪个验证覆盖？
2. 随便挑一张后面的任务卡，只看共享接口和这张卡，能直接动手吗？
3. 有没有一个接口被两个任务各自定义，或者名字相同但含义不同？
4. 错误策略里有没有简报没要求的条目？有就删掉。
5. 最大的技术风险是不是在大量施工之前就被验证了？
6. 有没有任务在实现一个已有成熟库或标准库就能做的通用组件？技术选型偏离了默认表的话，写了理由吗？
7. （有接口契约时）每个跨施工线的调用都有契约吗？每条契约的示例能覆盖简报里相关的验收样例吗？

任务超过 6 个、或者用户要求时，派 `reviewer` 子代理做计划审查（review skill 的“计划审查”），根据审查结果修改后再交付。

### 6. 交付
告诉用户：计划路径、架构一句话、任务数、风险与探针、你代为做出的工程决定。下一步：`/build`。
plan 阶段不写产品代码，也不把计划中的测试说成“已通过”。

## 涉及副作用、时序或外部设备时（否则跳过）
在错误策略和探针里回答清楚：写操作结果未知时能不能重试（不能就先查询状态）；
等待的事件由谁产生、超时后怎么办；验收断言是否真的等价于用户目标。
这些只针对真实存在的边界，不要套用到纯计算代码上。
