# 选技术栈：从用户答得上来的事实出发，默认选无聊、成熟、零运维的

用户（尤其是不懂技术的）判断不了框架好坏，但答得上来下面这些事。plan 从这些事实推技术，不从“现在流行什么”推。

| 事实 | 例子 | 影响 |
|---|---|---|
| 在哪运行 | 自己的电脑 / 自己的手机 / 给别人用的网页 / 公司服务器 | 决定形态 |
| 谁来用 | 只有自己 / 几个熟人 / 不认识的公众 | 决定要不要账号、权限、部署 |
| 谁来维护 | 没人（做完就不管）/ 用户自己偶尔改 / 有开发者 | 没人维护 → 零运维、零依赖 |
| 要不要花钱 | 一分不花 / 每月几块钱可以 | 决定能不能用付费托管 |
| 数据放哪、多重要 | 丢了无所谓 / 不能丢 / 不能给别人看 | 决定存储、备份、隐私 |
| 要不要离线 | 没网也要能用 | 决定能不能依赖网络服务 |

## 默认表（偏离要在计划里写理由）

| 情况 | 默认做法 |
|---|---|
| 自己电脑上的小工具、批量处理文件 | 单文件脚本（Python 标准库，或系统自带的脚本语言），双击或一条命令运行 |
| 自己电脑上要有界面 | 本地网页：一个 HTML 页面加一个很小的本地脚本；不做桌面应用框架 |
| 只在自己手机上用 | 手机系统自带的自动化（快捷指令等）或一个能加到主屏幕的网页 |
| 给几个熟人用、数据量小 | 静态网页 + 托管的表格或表单服务；不自建服务器 |
| 给不认识的公众用、要账号和数据库 | 一个成熟的全栈框架加托管数据库；这时才需要后端 |
| 要定时自动跑 | 系统自带的定时任务，或托管平台的定时功能；不自建调度服务 |
| 已有项目 | 沿用项目现有的语言、框架和工具（见 codemap），不另起一套 |

## 避开 AI 选型的常见毛病
- **偏爱流行技术**：不要因为常见就上 React、微服务、云函数、容器编排。先看默认表，满足需求的最简单那一档就是答案。
- **训练数据过时**：版本号、安装方式、API 用 context7 或官方文档核实，写进“约定”时注明出处。
- **做多了**：组件、要安装的东西、要注册的账号越少越好；优先用用户电脑上已经有的东西。
- **顺从用户指定的技术**：用户坚持的技术和目标冲突时（简报里会标【用户选择·已知后果】），在计划开头写明冲突和后果，照用户的选择做，不悄悄换掉。
- **只有开发者看得懂的交付**：给用户的说明只讲后果——要装什么、怎么启动、要不要花钱、坏了怎么办；不讲框架名。
  验收样例写成用户自己能做的操作（“双击桌面上的 X，看到 Y”），开发者用的测试命令另外写在任务卡里。

（选型原则参考 Dan McKinley 的 “Choose Boring Technology”。）
