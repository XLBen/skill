# 按风险选测试方法

只在简报或错误策略里确实有对应风险时使用。这张表选的是**测试方法**，不增加产品需求；
每个用到的方法都要对应到一条验收样例或错误策略条目。

| 风险 | 方法 | 最小做法 |
|---|---|---|
| 序列化 / 转换 | 往返性质 | 生成多种输入，断言 解析(输出(x)) == x，重复执行结果不变 |
| 不可信或格式错误的输入 | 边界与畸形输入 | 空、超长、错误编码、缺字段；断言按错误策略报错而不是崩溃或静默通过 |
| 接口或数据格式变化 | 契约测试 | 用消费方的期望检查生产方的真实输出 |
| 重复执行 / 重试 | 幂等 | 同一操作执行两次，断言状态和输出与执行一次相同 |
| 失败与恢复 | 故障注入 | 中途抛异常或超时，断言回滚或保持旧结果 |
| 并发 | 交错执行 | 并发或重复调用后，断言约定的不变量仍成立 |
| 数据迁移 | 对账 | 迁移前后行数和校验和一致；回滚路径也跑一次 |
| 权限 / 安全边界 | 反向测试 | 未授权请求被拒绝 |

规则：
- 测试必须能在缺陷存在时失败。写完后临时改坏一处代码，确认测试会变红，再改回来。
- 不需要每一行都用；只选与本项目风险对应的行。

## 性质测试（property-based）
例子测试只检查一个点；性质测试检查一条对所有输入都成立的规律，让测试库自动生成输入去找反例。
**只有代码真的有这样的规律时才用**，没有就写例子测试，这本身就是合理的结论。

| 规律 | 写法 | 适合 |
|---|---|---|
| 往返 | `decode(encode(x)) == x` | 序列化、格式转换 |
| 互逆 | `f(g(x)) == x` | 加密/解密、压缩/解压 |
| 对照 | `新实现(x) == 参考实现(x)` | 重写、优化、重构 |
| 幂等 | `f(f(x)) == f(x)` | 规范化、格式化、排序、去重 |
| 不变量 | 操作前后某个条件都成立 | 状态变换、余额总和、元素个数 |
| 容易验证 | `is_sorted(sort(x))` | 结果难算但容易检查的算法 |

- 从强到弱：往返/对照 > 幂等 > 不变量 > 类型不变 > 不崩溃。用代码能支持的最强那条；只能写“不崩溃”时，通常不值得引入测试库。
- 两种“什么都没测”的写法：
  - 同义反复：`assert add(a, b) == a + b`，用和代码相同的方法算期望值。要找一条约束结果、但不重算结果的规律。
  - 输入被过滤光：用 `assume()` 之类过滤掉几乎所有输入，测试“通过”了却没跑几次。约束要写进输入生成方式里。
- Python 用 Hypothesis，JS/TS 用 fast-check。项目还没有这类库时，引入它是依赖决定：在计划里问用户一次，并写出你打算测的那条规律。
