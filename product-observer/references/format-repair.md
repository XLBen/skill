# Format Repair (纠偏) — Product Observation

This document defines the **format-only repair turn** for
`product-observation/2` results. Its runtime text is generated by
`observation_results.repair_prompt` (see `scripts/observation_results.py`,
S09); this file is the human-readable counterpart of that prompt and must
stay consistent with it.

## 1. When repair is triggered

- The observer returns its **first answer** (exactly one ```json fenced
  block). The controller parses it and validates it with
  `observation_contract.validate_result_payload(payload, phase)`.
- If the reply is not a single fenced JSON object, or fails structural
  validation, the controller sends a repair prompt instead of re-observing.
- Budget: **1 first answer + at most 2 repair turns = at most 3 attempts
  total** (`run_format_repair(..., max_repairs=2)`).
- After the second repair the payload is still invalid → the round stops as
  `needs-observation` (repair cap). Nothing is fabricated to force an
  adoption.

Repair is a **shape fix**, not a second observation pass. It never reopens
the product and never re-runs the workflow.

## 2. The four prohibitions (四条禁令)

1. **不要操作产品** — do not run, click, screenshot, or otherwise touch the
   target product. No new observation.
2. **不要新增观察事实** — do not add surfaces, journeys, findings,
   evidence refs, or conclusions that were not already in the original
   payload.
3. **不要改变含义** — do not change severity, status, evidence references,
   or the meaning of any conclusion. Only field shape, enums, required
   fields, and value formatting may change.
4. **不要猜 controller 字段** — `goal_id`, `candidate_id`,
   `observer_session_id`, `model`, `packet_hash`, `received_at`, `attempt`
   are controller-owned. Leave them absent; never invent a value.

## 3. The two legal replies

Every repair reply must contain **exactly one ```json fenced block**.

**a) Corrected full payload** (`schema` is `product-observation/2`):

```json
{
  "schema": "product-observation/2",
  "phase": "discover",
  "stop_reason": "coverage-completed",
  "surfaces": [
    {
      "id": "S-01",
      "name": "Primary entry surface",
      "importance": "material",
      "modes": ["default"]
    }
  ],
  "journeys": [
    {
      "id": "J-01",
      "surface_ids": ["S-01"],
      "evidence_refs": ["evidence/j01.png"],
      "outcome": "covered"
    }
  ],
  "findings": [],
  "unobserved": [],
  "capability_gaps": [],
  "continuation": null,
  "evidence_refs": ["evidence/round.md"],
  "notes": "Minimal valid discover payload."
}
```

The repair prompt always embeds the complete legal template produced by
`observation_contract.result_template(phase)`; copy its structure and fix
only the reported fields.

**b) Marker — information is not sufficient:**

```json
{"repair_outcome": "needs-observation", "reason": "<缺少什么信息>"}
```

The marker is not a failure: it is the honest answer when the original
payload cannot be turned into a legal payload **without new observation**.

## 4. When to use the marker (信息不足 → needs-observation)

Use the marker instead of guessing whenever a missing/illegal part cannot be
restored from the already-recorded facts:

- `surfaces` is empty and no evidence reference allows recovering a surface
  id/name/importance.
- A `surface_ids`, `evidence_refs`, or required string is missing and no
  recorded value exists to fill it.
- Findings reference unknown surfaces that cannot be resolved from the
  payload's own surface list and evidence.
- A phase-required field is absent (e.g. `difference_classification` in
  `compare`) and the original observations do not support choosing a value.

Example (empty surfaces, nothing to recover):

```json
{"repair_outcome": "needs-observation", "reason": "payload has no surfaces and no evidence refs that could restore them; a new observation is required"}
```

Counter-example (wrong enum only — fix it, do not use the marker): the
payload says `"importance": "primary"`; the correct enum is `material` or
`peripheral`, and the original intent is unambiguous → return the corrected
payload with `"importance": "material"` only if the original observation
clearly supports it; otherwise use the marker.

The `reason` field must name what information is missing. Do not fabricate
surface/journey/evidence/conclusion content in the marker or in a payload.

## 5. State machine reference

`observation_results.run_format_repair(phase, first_text, send, ...)`
implements this document:

| Condition | Terminal status |
|---|---|
| valid first answer | `adopted` (`repair_count=0`, `attempts=1`) |
| invalid answer, repair budget left | send `repair_prompt(...)`, continue |
| valid reply after 1–2 repairs | `adopted` |
| marker received | `needs-observation` (marker `reason` preserved) |
| still invalid after 2 repairs | `needs-observation` (cap) |
| `send` raises | `failed` (exception text preserved) |

Terminal record: `{status, payload, problems, repair_count, attempts,
reason}`. Every received text is archived via `record_attempt` when a
`run_dir` is supplied, so both the invalid answers and the repair prompts
remain auditable.
