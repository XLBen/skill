# PUA Acceptance Protocol

所有阶段使用同一套短协议。阶段专用动作见 `stage-checks.md`；这里不重复定义
产品或 engine 的通过条件。

## 1. 进入验收

在提交产物、切换角色或宣布完成前：

1. 确认 `stage_id`、当前目标/切片、当前制品路径或版本身份。
2. 读取对应阶段检查卡，列出该卡要求的输入、范围和验收信号；区分门前证据
   与门后证据（见 `stage-checks.md` 的 Card Roles And Gate Phases）。
3. 区分四类事实：已经执行的证据、需要本席位执行的验证、需要主控执行的
   gate/动作（经 CONTROLLER_ACTION 请求，等待它不是失败也不是外部阻塞）、
   必须由 owner 决定的事项。
4. 输出一行 `[PUA-ACCEPTANCE]` 诊断，然后立即执行缺失的 agent-side 动作。

不要把“读取 skill”“列出计划”当作验收动作；验收必须看当前制品或实际输出。

## 2. 通用质询

### 目标对齐

- 当前阶段要交付的对象是什么？是否偷偷换成了更容易通过的对象？
- 原始请求、brief、goal、contract 或 PLAN 中的必需结果是否仍然覆盖？
- 本次检查范围是否包含真实公开入口，而不只是内部 fixture 或标签？

### 事实与证据

- 结论来自哪个命令、输出、文件、事件、评审发现或 owner 决定？
- 证据是否绑定当前制品、当前 hash、当前环境和当前验收范围？
- 是否检查了每个关键子进程、状态、输入快照和实际结果内容？
- 有没有把“命令写过”“exit 0”“文件存在”“截图看起来对”冒充行为通过？

### 主动查漏

- 当前缺口是实现缺失、验证缺失、授权缺失还是 owner 决策缺失？
- 修复一个问题后，是否检查同一根因、接口、共享实现和受影响调用链？
- 是否存在跳过、过滤、空测试集、mock 代替真实边界或 wrapper 吞错？
- 若信息不足，是否先查仓库、日志、一手文档和已有工具，再询问真正必要的问题？

### 交接

- 下一个角色能否仅依靠交接内容定位产物、证据和剩余缺口？
- 交接是否明确 `已满足`、`需修复`、`待 owner 决定` 或 `外部阻塞`？
- 若需要 owner，是否只提交事实和最小决定，不替 owner 选择？

## 3. 结果路由

### 已满足

所有适用检查均有当前证据，且阶段原有 gate 仍需正常执行。不要把 PUA 结果本身
写成 engine pass。

### 需修复

列出缺口、影响范围和下一步。修复后只重跑受影响验收；如果定义、接口或测试语义
发生变化，按现有 CR/goal 失效规则处理，不在 PUA 层偷偷修正状态。

### 待 owner 决定

说明事实、选项、成本/风险和需要的具体决定。暂停需要 owner 的阶段，不代答、
不继续执行不可逆动作，也不把等待算成失败重试。

### 外部阻塞

记录缺少的权限、工具、服务、凭据、真实边界或环境条件，说明已排除什么和最小
下一步。不能把阻塞改写成完成，也不能用 mock 或样例目录掩盖真实边界。

## 4. 返回格式

阶段执行者和子代理均使用以下短格式：

```text
[PUA-ACCEPTANCE]
stage: <stage-id>
result: 已满足 | 需修复 | 待 owner 决定 | 外部阻塞
scope: <本次实际检查范围>
evidence: <路径、命令、事件、输出摘要或 owner 记录>
gaps: <具体缺口；无则 none>
next: <交接、修复复验、等待的决定或升级动作>
```

`evidence` 必须引用真实可定位材料；`gaps: none` 不是跳过检查的许可。

## 5. 结束条件

一次有证据的验收即可结束。只有以下情况才追加检查：

- 当前制品发生实际改动；
- 发现新的失败信号或未覆盖的原始要求；
- 受影响范围扩大；
- owner 或既有 gate 要求新的验证。

不要为了“更有 PUA 味”重复同一条已经覆盖当前制品的验证，也不要用旁白、表格或
工件数量充当证据。
