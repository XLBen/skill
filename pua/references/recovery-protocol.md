# PUA Recovery Protocol

本协议把原版 L1-L4 的主动性接到本仓库现有 failure signature、no-progress、CR 和
owner 升级上。它不创建第二套状态机。

## Failure Counting

只统计同一子目标的**实际方案实验**：方案执行到预先定义的验收信号仍未满足，且有
可归因的失败结果。沿用 construction 的 normalized failure signature 和
mvp-delivery 的 no-progress 规则。

不计入失败：

- 读取文件成功或失败、搜索没有匹配、预期的 behavior-red；
- 等待 owner、等待授权、缺少尚未提供的外部服务；
- 仍在执行的任务、取消的任务或安全拒绝；
- 只换了 attempt ID、措辞、绝对路径、时间戳或随机 ID 的同一结果；
- 没有改变方案也没有执行实验的旁白。

## Escalation

### 第一次失败：L0

逐字阅读错误和上下文，验证最可能根因，做一个最小修复。保留命令、输出、环境
和当前制品身份。不要因为第一次红就说“无法解决”。

### 第二次同类失败：L1

原味提醒：“隔壁 agent 一次就过了。换个本质不同的方法，不要给同一方案换个参数
就算换路。”列出至少两个候选假设，选一个能区分它们的安全探针；如果是方法执行
偏差而不是方案问题，修正执行但不要假装换法。

### 第三次同一签名：L2 + 既有熔断

原味提醒：“底层逻辑是什么？搜索、源码、三个假设都做了吗？”执行下方七项检查，
整理三次原始结果、累计时间/成本、已排除事实和两个具体方案。随后进入现有
construction 三连败熔断或 mvp no-progress blocker；不得普通第四次重试。

### 更高等级

L3/L4 的原版话术可以用于升级报告和复盘，但不能扩大 retry 上限。继续工作只能由
既有 owner 决定、批准的 CR、恢复流程或新的可验证证据授权。用户锁定的风味不改变
事实计数和权限边界。

## Seven-Point Check

在第三次同类失败前后，记录：

1. 失败信号和完整相关输出是否逐字阅读；
2. 报错原文、官方资料、仓库用法是否搜索；
3. 失败位置的源代码/配置上下文是否读取；
4. 版本、路径、权限、依赖和输入假设是否用工具确认；
5. 是否反转过最初假设；
6. 是否在最小安全范围复现；
7. 是否换过工具、方法、角度或技术路径。

每项填写 `done`、`not-applicable`（附理由）或 `blocked`（附证据）。不允许用空勾
或“已排查”代替记录。

## Anti-Spinning Output

达到升级条件时返回：

```text
[PUA-RECOVERY]
target: <目标/步骤/outcome>
signature: <normalized failure signature or no-progress reason>
failed_experiments: <实际失败次数>
level: L1 | L2 | L3 | L4
facts: <已确认和已排除的事实>
methods: <已尝试的方法及各自结果>
seven_point_check: <七项结果>
options: <至少两个具体方案、成本和风险>
next: <既有熔断、CR、owner decision 或新证据条件>
```

`options` 不是要求用户替 agent 诊断，而是把可执行选择和事实交给 owner；能在当前
授权内继续的动作先做，不以升级报告替代工作。

## Iceberg Scope

“修一个查一类”只覆盖：同一根因、同一接口、共享实现、相同配置路径或当前修改
直接影响的调用链。发现同类问题：

1. 若影响当前验收，加入当前修复并复验受影响项；
2. 若属于原始目标但不影响当前切片，记录为后续 outcome/CR/SI，不偷偷扩大当前包；
3. 若是可选优化或无证据猜测，记录观察但不创建假 blocker。

当相关范围已检查、受影响验证通过、没有新失败信号时结束。不要用全仓随机扫描
制造“主动性”或无限工作。

## Honest Blockers

PUA 不能把以下情况改成失败重试：

- 缺少 owner 对产品取舍、brief、PLAN、SI 或 slice 的实际决定；
- 缺少危险操作授权、凭据、MCP、服务或真实外部边界；
- 既有 engine gate、CR、预算或安全规则明确阻断；
- 继续操作会产生未声明的不可逆、副作用或外部写入。

这些情况要带事实和最小下一步等待/升级。诚实阻塞是闭环的一部分。
