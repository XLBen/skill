# Review：三个审查点

每个审查点只回答它的清单，不要扩展成通用代码审查。审查结果中，每个问题都要给出：
**严重程度**（必须修 / 建议）、**位置**（文件:行，或任务 ID）、**依据**（看到了什么、运行了什么）。
没有依据的担心不要写成问题；风格偏好不算“必须修”。

## 1. 计划审查（reviewer 子代理，build 之前）
输入：简报路径、计划路径。逐项检查：
- 简报的每条验收样例，都能找到实现它的任务和覆盖它的验证吗？有没有简报没要求、计划却加进来的功能？
- 把每张卡片当作唯一的输入：只看共享接口和这张卡，执行者还需要自己决定跨文件的事情吗？（例如数据格式、函数放在哪个文件、调用哪个接口）
- 共享接口有没有重复定义、名称相同但含义不同、或者被任务使用却没有定义的情况？
- T01 是否打通了端到端？最大的风险是否在前面就验证了？
- 每个任务是否不超过 4 个文件？验证命令是否真的断言了内容？
- 错误策略里有没有简报没有要求的条目？（这些条目会变成防御性代码）

## 2. 任务审查（总控自己做，每个任务完成后）
先运行 `python .opencode/wf.py diffcheck <ID>`，再读 diff。worker 汇报为 `done_with_concerns` 时，先核实它提出的疑虑。检查：
- **范围**：有没有修改卡片“文件”以外的文件？有没有实现后续任务的功能？
- **接口**：共享接口里的签名、类型、输出格式是否原样使用？
- **防御性膨胀**：diffcheck 列出的每处 try/except、类型/空值检查、默认值回退、重试，
  能否对应到错误策略里的某一条？对应不上就是“必须修：删除”。
- **测试**：断言的是具体值吗？有没有为了通过而放宽断言、跳过测试或改动验证命令？
- **组织**：有没有新建 utils/helpers 之类的文件、单实现的抽象层、超过约 300 行的文件？
- **复用**：有没有重新实现 `docs/codemap.md` “可复用模块”里已有的功能？
- 并行施工时，`diffcheck` 加 `--cwd <worktree>`，检查的是 worktree 里的改动。

全部通过就 `wf done`。不要因为“写法可以更优雅”而打回。

## 3. 最终审查（reviewer 子代理，全部任务完成后）
输入：简报路径、计划路径、diff 范围（`git diff <起点>..HEAD`）。你可以运行测试和产品命令，但**不能修改任何文件**。

1. 对简报的每条验收样例，通过真实入口运行（CLI 就执行命令，服务就发请求），把实际输出和期望结果对照。
   这是最主要的工作，不能只读代码就下结论。
2. 运行完整的测试命令（计划“约定”里写的那条）。
3. 读 diff，对照计划：有没有漏做的任务要点？有没有计划之外的功能、文件或依赖？
4. 找一两个简报范围内、但验收样例没有覆盖的真实使用情况试一下（例如空输入、重复运行）。
   只有当结果明显违背简报时，才算“必须修”。

输出格式：
```
验收样例:
- [通过|失败] <输入> → 实际: <输出摘要>
测试: <命令> → <结果>
问题:
- [必须修|建议] <文件:行> <问题>。依据: <运行的命令或看到的代码>
结论: 可以交付 | 需要修复（列出必须修的编号）
```
