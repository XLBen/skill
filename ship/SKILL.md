# Ship：收尾交付

`wf` 指 `python .opencode/wf.py`。所有结论都要来自这一轮实际运行的结果。

## 1. 最终检查
1. 运行计划“约定”里的完整测试命令，以及 `wf regress`。
2. 通过真实入口逐条运行简报（含所有“变更 N”）里的验收样例，记录实际输出。
3. 有失败就停下：属于计划内的按 `build` 修复，属于新需求的转 `change`。

## 2. 文档
- 更新 README（或项目已有的使用文档）：安装、运行、示例。**示例输出从刚才的真实运行中复制**，不要手写。
- 新增的配置项、环境变量、命令行参数都要写进去。
- 只写使用者需要的内容；设计过程留在 docs/plan.md。

## 3. 清理
用 `git diff <起点>..HEAD` 检查（起点记在 plan.md 顶部）：
- 删除调试输出、临时文件、注释掉的代码、没被使用的函数和导入；
- 检查依赖清单：有没有计划之外新增的依赖；
- 不做计划之外的重构。

清理后再跑一次测试。

## 4. 交付说明
写给用户（中文，简短列表）：
```
完成: <一句话>
验收样例: <通过数>/<总数>（失败的列出来）
使用方法: <最常用的一条命令>
已知问题 / 限制: ...
需要用户做的事: <配置、密钥、部署步骤>
代为决定的事项: <plan.md 的裁定记录和【代定】项>
```

## 5. 合并方式
项目用 git 时，问用户选哪一个（不要替用户选）：
1. 合并到主分支
2. 推送并开 PR —— PR 描述包含：改了什么、为什么、怎么验证的、**合并风险**（会影响哪些已有功能、有没有数据迁移、如何回滚）
3. 保留分支，暂不处理

**推送、合并、部署之前必须得到用户明确同意。**涉及部署、对外服务或凭据时，先加载 `security-and-hardening` 和 `shipping-and-launch`（extras）检查一遍。
