## 未执行：DeepSeek / GLM 等模型的端到端效果

本轮没有实测指定模型的成功率、token 成本或返工次数；不得从单元测试数或上述
脚本实验推出“弱模型已稳定产出”。下面是重启/安装后可以实际执行的评估口径：

1. 选一个全新临时项目和固定需求（例如支持新增/查询/重启持久化的 CLI）；预先
   冻结验收场景，包含变化输入、错误输入、跨进程状态回读。不要拿示例原文考模型。
2. 用规划模型运行 grill→plan，保存完整设计。检查后续每步是否可执行、共享接口
   是否一致、技术依据是否真实；记录 build 仍需自行决定的架构/接口问题。
3. 切到实际可用的 DeepSeek/GLM 模型，用无访谈聊天历史的会话执行 build，只给
   目标/设计和 next-step 包。保存原生会话 trace，不人为代填它遗漏的执行记录。
4. 通过实际交付入口跑冻结的验收场景；模型说“通过”不算独立运行证据。桌面
   项目另有真实设备/窗口/驱动条件，不能把 CLI 结果外推。
5. 记录：验收是否通过、模型擅改接口次数、无新证据重试数、未授权范围扩张、
   首次真实边界验证前写了多少无关代码，以及实际 token/时间（缺数据写未知）。

先跑一轮观察失败，再针对缺陷改进计划/任务包并跑新候选；不一次生成一百个
工作流测试来代替真正使用。小样本也不能宣称任意软件和模型都有稳定成功率。
