# 工程设计反例走查

用于复杂设计发布前及重大 replan；简单项目只回答适用项，写明不适用原因即可。
不是增加一份表格来打勾：每条适用项给具体反例、证据、修订或未解除条件。

## 1. 从空项目推演施工

- 每条 preflight/验证命令的解释器、脚本、模块、配置和样本何时产生？
- 有无“先运行本步才能生成的前置探针”？依赖图有任务节点，还应包含这些前提。
- 分开环境可用、测试基础设施可用、业务行为 red；导入错误不证明业务测试有效。
- 需要人为准备的目标状态，谁准备、如何检查、build 能否重复进入？不把复杂导航
  偷塞进“测一下按键”而不估计它的成本和依赖。

## 2. 状态、时间与坐标的一致性

- 谁产生等待的事件？等待期间是否暂停了同一个生产者、占着锁或阻止了时间推进？
- 事件已发送、已被接受、业务已完成分别意味着什么？各自的观察和超时是什么？
- 看门狗是否知道预期暂停/网络退避/人工决定状态？不能把正常等待判为卡死重开。
- 坐标/单位/参考帧来自同一状态吗？移动相机后的点不能未建模就混进同一固定变换。
- 发现矛盾就阻断相关实现，不写“运行时调优”推给执行模型。

## 3. 副作用与不确定结果

- 为写操作定义：未发送 / 已发送结果未知 / 确认成功 / 确认失败。
- 验证超时不证明动作未发生。重试之前先查状态，使用幂等键、去重或补偿；无法
  核实时停止。购买、征召、提交订单等不允许“验证失败就再执行”的通用循环。
- 错误处理的保护边界是否比正常路径弱？重启/回滚是否会破坏用户数据或重复效果？

## 4. 验收与回退保持承诺

- 用户目标与机器断言是否等价？“省份属于我”不当然等于“目标国家已被吞并”。
- 删掉一个必要动作、用近似信息替代限制、放宽正确率或把“发生变化”代替“到达
  指定目标”，都是可能的范围变化，不能只写成 fallback 就自动获得授权。
- 分开：探索可行、单次演示、代表场景功能、长期可靠性、研究/策略效果。
- 阈值从业务需要、误判代价和实测依据推导；20 次里 16 次不推出任意长期故障率。
- 测试中一个标签消失可能是截图失败/进程退出，不必然表示按钮操作成功。

## 5. 运行预算与系统性失败

- 建模总耗时、存储、请求量和恢复损失：例如次数 × 实测单次开销 + 重试/停机开销。
  未知量安排有预算测量，不编造几个百分点成功率或固定天数。
- 无限重跑是用户选择的运行政策，不是纠正系统性错误的算法；相同失败签名需要
  诊断/重新规划，不能靠无限尝试假定最终成功。临时故障与设计缺陷分开。
- 备选方案也会消耗资源并引入状态；有回退不表示风险关闭。

## 6. 证据与用户可接受性

- 每个关键结论的证据是否真正支持它？区分文档/本机/代表场景，不做跨范围推论。
- 禁令的保护对象清楚吗？“形式更好看”不能使同样违反规则的效果合法化。
- 核心使用体验是否被具体说明：动作步骤、延迟、校准、设备占用、失败后损失？
- 高影响/陌生路线尽早给演示或具体样例；不能拿用户确认一个术语当作对所有后果的
  确认，也不能宣称没有视频的一切文字同意无效。记录确认范围与尚未知项。
- 用户中途异议记录在循环的决定请求中；暂停≠技术失败，“算了”≠自动批准。

## 审查输出

沿用已有 reviewer issue 格式：主张/反例 → 证据 → 受影响任务/接口 → 阻断与否 →
必要修订/实验/owner 决定。不要求 reviewer 再写一份完整设计，不为每个局部修复派席位。
结构完整、流程能讲通、所有检查脚本打印 PASS，都不能替代上述反例检验。
